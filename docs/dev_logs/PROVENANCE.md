# 游戏开发证据与留痕规则 (GameDev Provenance)

## 权威边界

- `records/` 保存唯一的游戏研发经历正文；引擎运行表现与测试提供客观事实，[Bible](../bible/_index.md) 规定当前有效的玩法、架构与体验契约，当前任务指令提供执行授权。
- 复盘是带来源的摘要，不替代原记录；历史建议不自动授权推翻当前核心玩法架构。
- 实质变化及时记录：正/负/未定结果、重要手感调优、严重Bug/物理穿模解决方案、机制与输入规则变化、放弃的方向或流派。
- 纯格式整理或微小代码清理无需新记录；收尾说明 `NO_DEV_DELTA` 及原因。

## 最小记录

每条记录使用稳定且唯一的ID（如 `REC-20260926-01`）和五节正文：
1. **问题与动机**：遇到了什么手感/性能/架构问题，为什么要改。
2. **尝试与条件**：具体修改了哪些参数、代码或场景配置，与之前的对照是什么。
3. **观察与证据**：实测效果、顿帧毫秒、物理表现或报错信息。
4. **解释与经验**：得出了什么结论，为什么成功或为什么废弃。
5. **关联与后续修正**：后续决策、是否合并入主干、修正了哪条旧记录。

正文每个要点优先一句话，参数对比优先最小充分表格；大段日志和长代码只引用文件相对路径与行号。

元数据中 `recorded_at` 为实际写入时间，`occurred_at` 为实际测试时间。
`scope` 明确引擎版本、测试场景、关键参数及适用范围。

## 来源与核验等级 (Status)

来源写明项目相对路径、代码行号/节点路径、SHA-256 和核验等级；不编造指纹。

| status | 含义 |
|---|---|
| `ingame_tested` | 在 Godot 引擎中实际运行测试过，验证了手感与无报错 |
| `playtest_feedback` | 拥有真实的玩家/试玩者反馈与实测数据 |
| `report_checked` | 读取了引擎控制台日志或已有性能报告，未实机重新测试 |
| `code_only` | 只完成了 GDScript 代码编写或场景搭建，尚未实机运行验证 |
| `conversation_only` | 讨论或设计头脑风暴，尚未落地为工程代码 |
| `snapshot_checked` | 核对过历史版本文本快照 |
| `unverified` | 来源不可本地核验，必须填写 reason 说明 |

发布前核对来源位置与参数，必要时用 `sha256sum <文件>` 计算指纹；本地实际检查过的来源必须提供真实指纹。
不把密钥、第三方私有凭据写入记录。

## 发布与修正

1. 按模板起草，检查必填字段、关键参数、测试条件和来源等级。
2. 检查ID未占用及 `related`/`corrects`/`supersedes` 目标存在，将审阅后的文件存为 `docs/dev_logs/records/<ID>.md`。
3. 同ID同正文可视为幂等完成；同ID不同正文须新建修正记录，保留旧文件。
4. 重要错误用 `corrects`，明确替代旧方案用 `supersedes`，一般关联用 `related`。
5. 收尾报告记录ID、路径与实际检查项；归档失败报告 `ARCHIVE_PENDING`、原因与草稿位置。
